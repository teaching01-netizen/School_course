# Course Expiry and Cycle Configuration Plan

## Contract

- `courses.expiry_days` is nullable. `NULL` means no expiration; `0` is valid.
- `courses.cycle_id` remains nullable and references `crm_cycles.id`.
- Update request fields are presence-aware: omitted preserves, JSON `null` clears, and a value replaces.
- `last_session_at` is `MAX(sessions.end_at)` for non-deleted sessions, including future sessions.
- `expires_at` is `last_session_at + expiry_days * 24 hours` when both inputs exist.
- `expiry_status` is `active`, `expired`, or `not_configured`; `not_configured` means no expiry days or no active sessions. `expired` starts at `server_now >= expires_at`.
- Lifecycle is informational. It does not filter or block scheduling, enrollment, absence, active-course, or list behavior.
- Cycles retain immutable `id`, `source_kind` (`imported` or `manual`), and nullable `import_key`; editable `display_name`, `start_date`, and `end_date` are date-only inclusive bounds with `start_date <= end_date`. Existing rows are imported source identities. `label` remains the non-null source/compatibility field used by imports and legacy consumers; `display_name` is the UI name and defaults to `label`. Manual cycles use an immutable client-supplied ID, `source_kind=manual`, `import_key=NULL`, and `label=display_name`.
- Cycle POST/PUT mutations require `Idempotency-Key`; follow `docs/idempotency.md`: exact request bytes replay the original response, while the same key with different bytes returns 409.

## Backend sequence

1. Add DDL migration `00101_course_expiry_and_cycle_config.sql`: `courses.expiry_days` with a database check `expiry_days IS NULL OR expiry_days >= 0`, cycle `source_kind` with default/constraint `imported|manual`, `import_key`, nullable `display_name`, `start_date`, `end_date`, preserve `label` for existing consumers, add a database check enforcing `start_date IS NULL OR end_date IS NULL OR start_date <= end_date`, and document that down removes data. Existing reads use `COALESCE(display_name,label)` until the backfill completes, so current cycle writes remain compatible. Do not backfill business rows in DDL: add a dedicated idempotent restartable `backend/cmd/course-cycle-backfill/main.go` command with advisory locking, cursor/resume behavior, dry-run, and operational invocation docs; it updates only `source_kind=imported` rows where `import_key IS NULL`, setting `import_key=id` and `display_name=label`, so reruns cannot convert or overwrite manual cycles. Add the production `(course_id,end_at) WHERE deleted_at IS NULL` index in a separate `00102_course_expiry_end_index.sql` `-- +goose NO TRANSACTION` migration per `docs/migrations.md`.

The derived query uses `MAX(sessions.end_at)` over `deleted_at IS NULL` and the new `(course_id,end_at)` index. Keep timestamps UTC, define `not_configured` for no expiry days or no non-deleted sessions, and use an injectable clock for boundary tests.
3. Make request parsing presence-aware for `cycle_id` and `expiry_days`; validate nonblank immutable cycle IDs, existing cycle on assignment, non-negative expiry, and preserve unrelated fields and explicit nulls through PATCH, PUT, create, and stale-edit responses. Test omitted/null/zero.
4. Update course detail GET, course list/overview, create/update responses, and stale-edit current. Confirm the `(course_id,start_at)` session index and add the end-at index in step 1. Extend `src/realtime/invalidation.ts` so `sessions:all` invalidates course detail/list queries, and add a `CourseDetail` realtime subscription effect that calls its existing `getCourse` loader when the current course is affected, because the page stores course data in local state. Bulk session edits first collect old and new course IDs inside the same transaction, then publish the deduplicated union only after commit; they do not publish from inside the loop. Series create/update/split/cancel/delete collect both old and new course IDs, and legacy-sync course/schedule writes in `backend/internal/legacysync/apply/course.go` and `schedule.go` publish both their existing events and course updates. Replace or bridge legacy outbox `course:<uuid>` events in `backend/internal/legacysync/outbox/publisher.go` to the supported `courses:all` channel, explicitly emit the internal course UUID as event ID (not the legacy external ID), retaining `sessions:all` for existing subscribers. Change `WithIdempotentTx` or add a result enum so callers can distinguish a newly committed transaction from a cached replay; publish lifecycle events only for newly committed transactions. Update all affected callers and add same-key replay event-count tests. Add query-bridge, local-course-state reload, and post-commit event regression coverage.
5. Centralize cycle configuration persistence in `backend/db/queries/crm_cycles.sql` and generated `backend/internal/db/crm_cycles.sql.go` plus custom DB methods, and add admin-only `POST /api/v1/crm/cycles` and `PUT /api/v1/crm/cycles/{id}` with exact-byte idempotency, validation, and authorization tests. POST requires an immutable nonblank ID, writes `source_kind=manual`, and rejects collisions with either an existing manual row or an imported row; imports encountering a manual-ID collision reject the import transaction rather than reusing or overwriting the manual row. Enforce unique `import_key` for imported rows. PUT rejects ID changes. Keep GET backward-compatible while returning configured fields.
6. Update direct cycle writes in `backend/internal/crmimport/import_service.go` and `backend/internal/crmimport/snapshot_service.go`, their generated/custom query callers, `backend/internal/crmimport/upload_v2.go`, and `CrmCyclesDeleteUnused` callers to share source-label upsert and active-snapshot cleanup. Refactor the v2 upload path and `SnapshotService` around one transaction-scoped import operation: stage rows, cycle upserts, cleanup, and snapshot activation commit together. New imported rows write `source_kind=imported`, `import_key=label`, and `display_name=label` on insert; existing configured `display_name` and dates are never overwritten, and reads still coalesce null values during backfill. The source identity is the incoming source label stored as `import_key`; the current schema has no independent upstream cycle key, so a changed source label is a new imported identity, while the old row is retained when course-referenced and otherwise eligible for active-snapshot cleanup. Imports update `label` only for imported rows and never overwrite `display_name` or dates; manual PUT updates `display_name` only and leaves `label`/`import_key` unchanged. `crm_rows` cleanup uses the active snapshot ID from `crm_state`; preserve configured fields, never delete course-referenced cycles, and never delete manual cycles. A manual-ID collision rolls back staged rows, cycle changes, snapshot activation, and leaves the previous active snapshot unchanged.

## Rollback

The migration has a reversible down path, but it removes expiry and cycle configuration columns. Roll back application binaries first and take an explicit database backup before using down; normal delivery is additive and does not use down.
