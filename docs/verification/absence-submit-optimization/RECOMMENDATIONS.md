# Recommendations and remaining obligations

No production implementation was changed by this verification. The added Go tests and pinned Lean package provide reviewable evidence for the current optimization.

1. **High: establish the intended authorization time boundary.** Snapshot-scoped authorization is modeled and tested. Strong commit-time authorization across schedule/config changes is NOT ESTABLISHED. Ordinary staff paths validate before their later selected-session fence (`staff_create.go`, `staff_create_tx.go`), versions are optional, and the post-fence recheck covers existing sit-ins rather than recomputing every expected-class/policy fact. Reproduce the schedule-edit trace in PRODUCTION_TEST_PLAN.md using the actual scheduler. If commit-time validity is required, take the relevant fences before validation or revalidate after acquiring them; add a barrier regression. Do not add a cross-request eligibility cache.
2. **High: complete writer and environment coverage before declaring production correctness.** The model requires cooperating writers and valid initial data. Inventory direct assignment helpers, schedule-issue resolution, roster/configuration changes, legacy sync and deployed old versions. Verify locks, invariant queries, primary reads and durability on the actual deployment. Formal status alone cannot discharge this requirement.
3. **Medium: stop immediately after a failed student lock.** `createAbsenceRecordTx` in `batch_routes.go` writes an error on `LockStudentForAbsenceSubmission` failure but lacks the immediate `return createdAbsenceRecord{}, false` used by other callers. PostgreSQL/context errors normally make later queries fail, and no unsafe commit was demonstrated, but error-flow correspondence is incomplete. Add the return with a fault-injection test asserting that no downstream query runs after lock failure. This pre-existing issue was recorded rather than silently bundled into verification.
4. **Medium: preserve coherent catalog ownership at all mutation boundaries.** The policy apply API's seenCourses checks support the AUTH assumption, while table-level direct and merge uniqueness alone do not prohibit a direct mapping and its mapped group both covering a member. Audit non-API writers. If they exist, centralize equivalent validation under a common DB lock/constraint strategy and prove/test the refinement; do not assume this condition because the primary endpoint enforces it.
5. **Contract clarification: retry safety is bounded.** Reuse the same actor/scope/key and request fingerprint for one logical operation while the stored key is retained. Document the existing 24-hour UI expiry and cleanup behavior. A changed key is a different operation; extending deduplication beyond expiry would require a durable business-operation identifier or a separate uniqueness contract.
6. **Conditional on a product requirement: notification delivery needs its own protocol.** Current after-commit SMS/email work is outside the proven atomic state transition. If eventual or deduplicated delivery is required, specify it and use a durable dispatch/outbox design with fault/replay tests. The present verification makes no such delivery claim.

The selected-target and selected-session optimization needs no additional runtime change for the static coherent snapshot envelope exercised here. Production readiness remains CONDITIONAL on the critical assumptions and open refinement obligations; whole-production correctness is NOT ESTABLISHED.
