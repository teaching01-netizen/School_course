# Follow-up decisions

1. Define when a policy revocation takes effect. The counterexample shows a booking whose validation preceded revocation and whose commit followed it. If commit-time eligibility is required, use a common version or lock on the relevant policy rows. Booking and all mutation paths must coordinate through it so a committed change cannot slip behind the last check. Establish the lock order before implementation and require the barrier regression to reject or revalidate the earlier booking.
2. Return immediately on a failed student lock in the per-item student and shared staff transaction helpers. Both currently write an error response and then continue. A failed query normally poisons the transaction, but a no-row result is a separate case. Add a fault test asserting that failed acquisition neither attempts nor commits a booking. This is a source finding without a reproduced erroneous commit.
3. Ship the tested revisions and repeat the staging checks using the deployed source SHA and the actual environment settings. Keep idempotency claims bounded to the retained key window. Confirm database failover, stale-asset compatibility and retry behavior before extending the production verdict.
